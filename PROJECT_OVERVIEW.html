Polymath — Musk Tweet Count Trading Bot

A high-frequency forecast-driven market-maker / taker for Polymarket weekly "How many tweets will Elon Musk post in [date range]?" prediction markets. Combines a probabilistic tweet-count forecaster with a multi-bin Kelly optimizer over a shared capital pool, executing FAK orders through Polymarket's CLOB v2.

1. TL;DR for a New Collaborator

The bot trades a family of Polymarket markets that pay $1 if Musk's weekly tweet count lands in a specific bin (e.g., 250–274) and $0 otherwise. Every week a new event launches with ~21 bins and runs Mon noon ET → following Sun noon ET.

  • Edge source: We model the count distribution better than the crowd, especially during the contract week as tweets arrive.
  • Forecaster: Separates intraday (today's partial count → today's final) from interday (future days' totals), then convolves via Monte Carlo. Refits daily at noon-ET rollover; nowcasts much more often.
  • Sizing: Multi-bin fractional Kelly with CRRA power utility — bins are mutually exclusive so we co-optimize. Default κ = 0.25 (¼-Kelly).
  • Execution: FAK (fill-and-kill / IOC) limit orders via py_clob_client_v2. No resting orders, no market orders. Sells prioritized over buys.
  • Concurrency: One GASKellyTradingBot per active event, all sharing a single CapitalPool, EventStore, WebSocket, and user-stream listener.
  • Two-loop tick: a slow loop (~150 s) refreshes the forecast; a fast loop (~15 s) re-reads orderbooks and runs Kelly. Sync-driven mode also runs a tick within ~10 s of an XTracker lastSync change.
  • Collateral: pUSD (1:1 wrap of USDC.e via the Polymarket CollateralOnramp). Wrapping is an opt-in operator CLI, never automated.
Key files to know cold: forecaster/forecaster.py, forecaster/multi_event_manager.py, kelly/executor.py, kelly/kelly_math.py, forecaster/run_multi_event.py (entry point).

2. The Market

2.1 Mechanics

Each weekly event has ~21 mutually exclusive bins: 0–74, 75–99, 100–124, …, 525–549, 550+ (see default bins in forecaster/config.py:351–373). Every bin is a binary market with a YES token and a NO token. Exactly one bin's YES wins ($1); all other bins' YES lose ($0). Conversely, exactly one bin's NO loses; all others win.

Settlement happens at the Sunday noon-ET boundary on the strict tweet count reported by Polymarket's XTracker archive (xtracker.polymarket.com). XTracker is the authoritative count source — not Twitter's API.

2.2 Why there is edge

  • The crowd anchors on round-number bins and overweights the modal range.
  • Tweet arrivals are bursty (Hawkes-like); the crowd misprices both quiet stretches and bursts.
  • Time-of-day and day-of-week effects are sizeable but easy to forget during the week.
  • Late-week boundary "cliffs" (e.g., 5 tweets away from the bin's upper edge with 3h left) are mispriced because retail can't size them.

3.1 The two-loop runtime

Each event's GASKellyTradingBot runs two concurrent coroutines:

LoopCadenceJob
Slow loop slow_loop_interval_seconds = 150 s Refresh forecast (intraday nowcast + sum distribution + bin probabilities). Cached for 165 s.
Fast loop fast_loop_interval_seconds = 15 s Re-read orderbooks, sync portfolio, run Kelly iteration, place candidates.
Sync-driven tick Poll lastSync every 5 s, debounce 15 s Within ~10 s of an XTracker sync change, recompute count + run a fast tick. This is what lets the bot react to new tweets in near-real-time.

4. The Forecaster

The forecaster's job is one thing: produce a probability vector over the ~21 bins, given the current tweet count, time within the contract week, and historical data. Everything else is plumbing.

4.1 Decomposition

The week-total is decomposed as

Nweek  =  Ntoday  +  Σh=1..H Nday h

Two distinct models cover the two terms:

  • Intraday model — given today's partial count, project today's final count.
  • Interday model — given a history of daily totals, sample each remaining day's total.

Both are pushed through a Monte Carlo simulator (forecaster/monte_carlo.py, 10–25k paths by default) that produces a sample of Nweek; a ProjectionModel (forecaster/projection.py) converts the empirical sample into the bin-probability vector used by Kelly.

4.2 Intraday: two modes

ModeIdeaWhere
ridge Empirical progress curve F(τ) (cumulative-fraction-of-day by minute) + burst features (15/60/180-min counts, time since last tweet) → ridge-regressed log-normal nowcast. Std decays as √(1−Fτ) so confidence tightens late in the day. intraday.py
bucket Day split into 8 buckets, each with a Negative-Binomial rate. A Hawkes-style impulse curve λ(τ) (1-min res, Gaussian-smoothed) captures diurnal pattern; recent activity boosts near-future rate with ~30-min half-life. Multiplier clamped to [0.4, 3.0]. intraday.py (Bucket* classes)

4.3 Interday: three swappable regime models

Configurable via forecaster.interday_model (config.py:334):

ModelLikelihoodStrength
EWMA (default) NegBin around EWMA of log-intensity Robust, fast, ~3-day memory at α = 0.35; mean-reverts toward the 7-day weighted mean for distant horizons.
NB-GAS Negative Binomial with Generalized Autoregressive Score recursion Faster regime adaptation via Pearson-score feedback; MLE-fit.
PIG-GAS Poisson–Inverse-Gaussian with GAS recursion (pig.py) Heavier tails than NB; better for occasional extreme days. Variance = μ + σ2μ2.

4.4 Dispersion & weekend effects

  • Dispersion: rolling NB k estimated by method-of-moments with 14–45-day half-life (interday.py:217). Floor at k=0.5, cap at 100. Tuned via dispersion_inflation_factor (default 2.5) which widens the tail; grid search showed 2.5 yields ~88–92% coverage on the held-out test set.
  • Weekend: multiplicative factor (~0.7–1.3) per Saturday/Sunday, 14-day half-life (interday.py:339).

4.5 Regime adjustment (Bayesian shrinkage)

Today's partial count gives a noisy estimate of "today's regime intensity." Rather than fully trust or fully ignore it, the forecaster runs a 1-step Kalman update in log-intensity space (monte_carlo.py:246–320):

σobs2 = σ02 / Fτ   →   adj = clamp(posterior_mean, 0.9, 1.1)

The adjustment decays across horizons: day-1 gets full signal, day-6 gets ≈ 3 % at decay = 0.5. Gated to fire only after 6 h into the day and once F(τ) ≥ 0.20 — otherwise it amplifies noise.

4.7 Projection: empirical sample → bin probabilities

The default AsymmetricProjection (projection.py) uses the raw Monte Carlo sample directly: pi = fraction of paths landing in bin i. This preserves the empirical right-skew (~0.4 in this market). Alternatives — NormalProjection, GammaProjection, SkewNormalProjection — fit a parametric form to the same sample, occasionally useful for tail bins where the empirical sample is sparse.

5. The Kelly Optimizer

Bins are mutually exclusive: exactly one bin's YES wins (and equivalently, exactly one bin's NO loses, all other NOs win). That means we can compute, for each possible winner j, the terminal wealth of the entire portfolio:

Wj  =  C  +  qYj  +  Σi≠j qNi

where C is cash, qYj is YES shares in the winning bin, and the sum is NO shares across all losing bins (each pays $1). Under CRRA utility U(W) = W1−γ/(1−γ) with γ = 1/α (and the log limit at α = 1):

c*YESi  =  (pi · Wi−γ) / S  ,  S = Σj pj Wj−γ

This reservation price is the fair value at which the optimizer is indifferent. Implemented in kelly/kelly_math.py:123–189 (compute_reservation_price_yes / _no). Default kappa = 0.25 (¼-Kelly) for risk control.

5.1 Candidate generation

In kelly/candidates.py, for every (bin, side) the optimizer estimates marginal utility of a small screening chunk (default $2 USD) and ranks all candidates by utility gain per dollar spent. The top candidate above min_buy_utility = 0.003 / min_sell_utility = 0.004 is executed. Sells get a higher threshold (hysteresis) and are prioritized over buys in the same tick.

5.2 Stake-based ROI edge gate

Before sizing, candidates pass an ROI gate (candidates.py:151–328):

  • BUY YES: market ≤ (fair − friction) / (1 + r)
  • BUY NO: YES ≥ (fair + friction + r) / (1 + r)

where r (required_roi, default 5 %) is the minimum return on stake, and friction is adaptive: 4 % in the tail (p ≤ 10 % or p ≥ 90 %) versus 2 % in the body. This is what stops the bot from cycling micro-trades on near-fair prices.

5.3 Take-profit (no stop-loss)

kelly/take_profit.py activates in the last ~4 hours before settlement when:

  1. Current count is within max_distance_to_next_bin of the current bin's upper boundary.
  2. Silence (no tweets) exceeds an adaptive threshold that shrinks toward settlement.
  3. YES price > trigger level with enough orderbook depth.

There is no stop-loss. Exits happen because Kelly says current holdings are no longer optimal (which automatically generates a SELL candidate) or because the take-profit module fires. This is intentional — bins are settled positions, not perpetual futures.

5.4 Portfolio bookkeeping

Each bin has a BinPosition (kelly/portfolio.py:27–248) tracking YES/NO shares, average cost, realized P&L, and a key innovation: unpriced inventory. When a fill arrives via WebSocket before the positions REST API has propagated, the executor stores shares with a conservative reserve price (max(1, price_at_acquisition)) and re-prices only after the REST sync confirms cost basis. This kills a class of "ghost double-buy" bugs.

6. Executor & Order Flow

Figure 2. Execution flow: forecast → candidates → FAK order → fill back to portfolio, with the integrity layer monitoring delta consistency.

6.1 Order placement

kelly/executor.py:456–528:

  • Type: OrderType.FAK (Fill-And-Kill / IOC). Fills what it can, cancels the rest. No resting orders, no market orders.
  • Price: SDK handles tick rounding (0.01 / 0.001 / 0.0001 depending on market).
  • Size: math.floor(size) (integer shares). Minimum: 1 share to sell; for buys, ≥ 15 shares OR ≥ $1 notional.
  • FAK price tweak: _best_fak_price (executor.py:117) bumps the price ± a few ticks if the natural maker_amount would round to > 2 decimals (an exchange constraint).

6.2 Cancellation

Because every order is FAK, the exchange auto-cancels unfilled remainders. The bot rarely calls cancel_order explicitly. The v2 SDK exposes cancel_order(OrderPayload), cancel_orders(hashes), and cancel_all() — used as a safety net on shutdown.

6.3 Fill reconciliation: the overlay pattern

Fills can arrive two ways:

  1. User-stream WS push (low-latency, ~< 1 s after match).
  2. REST positions API (authoritative cost basis, ~1–2 blocks lag).

The executor maintains an OverlayFillFragment set (executor.py:225) — confirmed-but-not-yet-REST-visible fills. Kelly plans against base_state + overlay; once the REST sync contains the fill, the overlay fragment retires. This prevents the bot from re-buying a position it has already acquired.

6.4 WebSocket subscriptions

StreamTopicFile
Orderbook Per-token YES + NO L2 (dynamically subscribed per active bin) kelly/websocket_client.py
User stream Authenticated: MATCHED → CONFIRMED events, deduped by match_id kelly/user_stream.py

Both streams reconnect with backoff and emit heartbeats (10 s for orderbook, 30 s for user stream). The user-stream listener is owned by MultiEventManager (one connection for the whole process); it routes (token_id) → (event_id, bin_index, YES/NO) via the global token_id_to_event map and pushes the fill into the right bot's overlay queue.

7.2 Phantom eviction

Post the V2 cutover (2026-04-28), Polymarket has occasionally re-listed a weekly market under a new event_id while the original event_id is still visible in old API responses but returns 404 on every order/book call. Production log showed 65,096 "No orderbook exists" 404s caused by this. Fix (commit 1c04fe9):

  • Track per-event miss count when Gamma discovery doesn't return the event.
  • If missed_count ≥ 2 AND event has zero positions AND zero pending orders → cancel its task and remove from _active_events.
  • Reset counter on reappearance.
  • Hard safety: any exception in the exposure check is treated as "has exposure" (eviction blocked).

7.3 Settlement P&L logging

Until commit a57e05f, realized_pnl was structurally $0 on every event completion because _cleanup_event returned allocated_capital as final_value. Fix: at cleanup, fetch the authoritative tweet count via get_authoritative_count, compute per-bin yes_pnl + no_pnl against the actual winning bin (inclusive bounds, +∞ for the top bin), and emit a structured [EVENT][SETTLEMENT_PNL] log line. Capital pool flow is unchanged — this is purely additive observability.

8.2 The EventStore (shared)

A single EventStore instance (forecaster/data.py) holds the entire tweet history (last max_event_store_days = 60 days), indexed by contract-day (noon-ET boundary). Bot instances read from this one store, eliminating duplicate API calls when multiple events are active. Authoritative refresh path:

  1. Poll lastSync every 5 s.
  2. On change, fetch new posts; debounce additional changes within 15 s.
  3. Rebase any affected contract-day's count to the XTracker trackings value (atomic).
  4. Notify all active bots → each runs a fast tick.

Soft deadline 10 s from sync-detect to trade; production p50 is well under that.

9. Capital & Collateral

9.1 CapitalPool

Single shared pool (kelly/capital_pool.py). Each event requests up to max_per_event (default $500; config currently $100). Returns capital with realized P&L at settlement. Re-syncs from on-chain pUSD balance every capital_sync_interval = 3600 s. Phantom-capital is a per-bot concept (capital_multiplier) that inflates Kelly's perceived wealth without actually consuming pool capital — used to size bigger when conviction is high without breaking the pool's allocation accounting.

9.2 pUSD / USDC.e onramp

CLOB v2 settles in pUSD, a 1:1 ERC-20 wrap of bridged USDC.e on Polygon, minted by the CollateralOnramp contract at 0x9307…B8ee. The bot does not auto-wrap. On startup if pUSD balance < threshold, it fails fast with a friendly error pointing at scripts/wrap_usdce_to_pusd.py, the standalone operator CLI. Reasons:

  • Wrap is irreversible (no unwrap method).
  • Hot path should never sign chain transactions outside of order signing.
  • The first wrap should be intentional and small ($1 dry-run available via --check).

Library at src/algo/musk_tweet_count/poly_collateral.py: get_pusd_balance, get_usdce_balance, approve_onramp, wrap_usdce_to_pusd.

10. Integrity & Reliability

Several layers exist specifically to fail safely when the exchange or our state model disagree:

LayerBehavior
IntegrityState (executor.py:271) Counts consecutive REST-vs-overlay mismatches; on threshold, freezes trading for the event with a deadline.
Balance/allowance refresh Before any SELL, refresh token balance + allowance; if mismatched, abort the candidate and emit BALANCE_ALLOWANCE_ALERT.
API sync gating Restart-restored events wait restart_required_stable_syncs = 2 consecutive stable syncs before resuming trading (avoids acting on stale snapshots).
Max data age Skip trading if EventStore data is > max_data_age_seconds = 300.
Settlement P&L log Per-event [SETTLEMENT_PNL] with per-bin breakdown at cleanup (commit a57e05f).
Phantom eviction 2 missed discovery scans + zero exposure → safely drop event (commit 1c04fe9).
Slack notifier Startup digest, hourly health, fill digest, integrity freeze/recovery, capital re-sync alerts.

13.5 Hard-won lessons (project memory)

  • No hard arbitrage within Polymarket. Soft (probabilistic) edges only.
  • Strict settlement metadata parsing + compatibility classification before cross-venue probability comparison.
  • Maker orders must enforce postOnly=True or non-crossing prices. Currently moot — we don't make resting orders — but if you add them, this is the rule.
  • Never linearly interpolate digital probabilities. Interpolate call/spread prices or variance instead.
  • Musk V2 orderbooks were unmigrated until 2026-04-28; post-cutover, non-Musk markets work; some phantom re-listings observed (fixed by eviction logic).
